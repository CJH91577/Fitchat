# Fitchat 手机端走查清单（演示版）

> 这份清单是给「人」照着做的，不是给自动化测试跑的。测试只能验证逻辑，验证不了布局——文字溢出、标签碰撞、点击区域过小，只有实际渲染出来看才会发现。
>
> 请用手机尺寸实际点一遍。发现问题就按 **页面 / 现象 / 复现步骤 / 期望行为** 记下来，先别急着改。

## 一、怎么打开

项目就是这个仓库本身（`C:\Users\admin\Fitchat`）。在终端进入该目录并启动：

```bash
cd C:\Users\admin\Fitchat
npm run db:seed   # 首次：建库 + 迁移 + 播种（会自动带上演示账号口令与三个邀请码）
npm run dev
```

等它打印出地址后，在浏览器打开 `http://localhost:3000`。

**打开后第一件事是登录**：未登录访问任何数据页都会被送到 `/login`。登录页上：

- 点**「先看看演示账号」**就能进去（演示账号：`demo@fitchat.local` / `fitchat-demo`，口令是公开的）；
- 或者用随部署附送的一次性邀请码（`FITCHAT-DEMO-1/2/3`，各可用一次）注册自己的账号——新账号里没有数据，会先走一遍首次引导填资料与目标。

- 依赖已经装好了（`node_modules` 就在这个目录里）。如果哪天提示找不到依赖，先跑一次 `npm install`。
- 如果它提示端口被占用（"port 3000 is already in use"），说明已经有一个在跑了，直接打开 `http://localhost:3000` 即可，不用重复启动。
- 浏览器里模拟手机：按 `F12` 打开开发者工具，点左上角「手机/平板」图标（Toggle device toolbar），把尺寸设为 iPhone 尺寸（390×844，或直接选一个 iPhone 机型）。
- 用真手机看（推荐，这是手机优先的产品）：让手机和电脑连同一个 Wi-Fi，启动 `npm run dev -- --hostname 0.0.0.0`，在电脑上运行 `ipconfig`，找到「无线局域网适配器 WLAN」里的 IPv4 地址（形如 `192.168.x.x`），在手机浏览器打开 `http://<那个IP>:3000`。注意：这会把服务暴露给同一局域网内的其他设备，用完记得停掉服务。

## 三、演示数据里容易误判的几个状态（实测，不是推测）

以下是**实际跑出来的数字**，看清它们能避免把正常数据当成 bug：

**「今天」就是打开网站当天的真实日期（北京时间）。** 页面按请求渲染，所以「今天」的数字每天都在变，也不会因为重新构建而变化——下面**带具体日期的**例子是历史数据，永远不变；「今天」的数值以你打开站点时看到的为准。另外：训练计划与运动记录**互不对齐**是有意保留的——记录反映的是实际发生的事，不是计划的事，练了计划外的项目与跳过计划都是真实场景。想看别的状态，用日历页点开任意一天即可。

**「圆环恰好满环」是可达的**，与旧版清单的说法相反。实测：

- **2025-09-24** 与 **2025-10-22**：热量恰好 1800（满环）
- **2026-02-23**：运动恰好 500（满环）

这三天的圆环会画成完整一圈，圆头线帽在 12 点方向重叠，可能凸出一个小点——**请按 D4 专门看一眼**。

**「超出」标记也是可达的**（下面这些是历史数据，永远不变）：**2025-09-30**、2025-10-04、2025-10-06 这三天摄入超标，点开就能看到图例里的「超出」。约四分之一的日子会超标——具体天数随数据覆盖范围变化，不用记。

**其余量级参考**（用来判断界面上的数字是否离谱）：

- 摄入盈余大致在 **−500 ~ +450** 千卡之间浮动，多数日子不超标
- 无运动的天数约占**四分之一**（休息日是设计的一部分，不是 bug）
- 体重序列：从 **2025-09-22 的 77.9kg** 一路降向目标 65kg（当前值见「我的」页）

> 上表中带具体日期的部分是历史数据，永远不变；带「今天」「约四分之一」这类总量或相对说法的部分会随时间和数据覆盖范围变化，核对时以你打开站点时看到的为准。

## 四、已知限制：现在还差什么

务必读一遍，别把演示当成品：

- **演示账号里的数据是按日期生成的**：它不是写死的常量，但也不来自真实记录。**真实账号写入的数据是真的**——落在 SQLite 里，重建容器也不丢。
- **口令没有自助找回**（没有邮件服务）：忘记口令时由管理员生成一次性重置码（`npm run reset-password`，24 小时有效），用户在登录页「忘记口令」里设置新口令；旧口令随即作废。见 DEPLOY.md 第四节。
- **邀请码只有随部署附送的三个名额**（写在 `lib/db/demo.ts`，是公开的）。它们限的不是「谁能进」，而是「陌生人能注册几个账号」——每个码只能用一次。要真正控制入口就换成自己的码（DEPLOY.md 第四节）。
- **一句话解析是词表 + 量词换算，不是模型**（`lib/data/meal-parser.ts`）：只认食物库里的词，份量写在食物**前面**（「两个鸡蛋」认，「鸡蛋两个」不认）。认不出的部分会列给用户，不会静默记成 100 克。**没有接任何大模型**；因此真实写入的条目里不会出现「AI 估算」标签——那个标签目前只存在于演示数据里（由生成规则打上）。搜不到的食物可以**自己录一条**（名称 + 每 100 克营养值，记录页「自己录一条新食物」），录完立刻可搜、可用来记一餐，同名冲突会明确提示。
- **每日目标是估算**：Mifflin-St Jeor × 活动系数，误差 ±10% 上下；蛋白与脂肪按体重定、碳水吃剩下的热量。界面上说成「算出来的建议值，可以改」。
- **运动消耗也是估算**：按分钟数（有氧，含强度系数）或组数（力量）估，没有心率、没有体重参与。
- **训练计划可以编辑**（每星期的主题与动作，改完「今天该练」与记录页的预填跟着变）；体重可以补记过去的日子（首页与某日详情页都能记，未来日期会被拒绝）。
- **错误监控是文件日志 + docker logs**（没有外部监控服务）：请求内出错记成 `request-error`（带路径与方法），进程级异常记成 `fatal`，访问日志每个请求一行；文件在 `data/logs/`（每日一个，保留 14 天）。看日志的方法见 DEPLOY.md 第七节。
- **「今天」按请求算**（北京时间），所以站点不会「过期」，也不需要每晚重建。演示数据多播到「今天 + 90 天」，且**启动时会自动续播**：演示账号最新记录日期距「今天 + 90 天」不足 7 天时，自动补到 90 天（只补最新日期之后的区间，用户改过、删过的行都不碰）。唯一的例外：站点连续运行超过 90 天且从未重启，续播没有机会执行，首页会显示「未记录」——重启容器即恢复。
- **训练计划与运动记录互不相关**：计划是一张周表（可以编辑），记录是真实写入的，两者不会自动对齐——这是刻意的，记录反映实际发生的事。
- **记录的起点是「用户开始使用日期」**（演示账号为 2025-09-22，新注册账号为注册当天），该日期之前的日期没有数据；界面对「还没开始使用」与「当天没有活动」是区别对待的。
