- **日期**：2026-10-01

## 1. 背景与定位

计划 1 交付了一份**可点击的设计稿**：所有数据按日期生成、不落库、无认证。它完成了自己的使命——让产品形态可见、可评估。

这份计划是**从「假数据 demo」跨到「真实多用户服务」的第一步**。它要建立数据持久化、账号体系与数据隔离这三样东西，因为后面四份计划全部依赖它们：

| 计划 | 内容 | 依赖 |
|---|---|---|
| 3 | 目标计算与身体数据 | **本计划** |
| 4 | 饮食记录与食物库 | **本计划** |
| 5 | AI 解析层（DeepSeek） | 计划 4 |
| 6 | 运动记录与训练计划落库 | **本计划** |

**做完本计划之后的应用形态**：能真实注册登录、真实保存个人资料与目标、真实记录并查看体重；**饮食、运动、训练计划仍是演示数据**。这是一个刻意的过渡状态，不是半成品。

---

## 2. 已确认的决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 数据与账号落地 | **境外托管 + 邮箱密码注册** | 零资质、零备案、当天可跑；与「先邀请制验证」的定位一致 |
| 邮箱发信 | **不发信** | 邀请码即门槛；省掉邮件服务与 SPF/DKIM 配置。代价：忘记密码无法自助找回 |
| 计划边界 | 地基 + 账号资料 + **体重记录** | 体重是「每个用户各自拥有的记录」里最便宜的一种，能跑通完整的写入→读取→隔离链路 |
| 技术方案 | **Next.js 单体 + Prisma + 托管 Postgres + 成熟认证库** | 认证与权限逻辑留在自己的代码里，出错有完整堆栈；不用 Supabase 全套以避免逻辑分散 |
| 页面取数 | **服务端组件直读** | 省一层；数据库凭据永不进浏览器 |
| 错误监控 | **本计划接入** | 本计划是第一次真正对外提供服务 |

## 3. 范围

### 3.1 做什么

1. 托管 Postgres 与 Prisma schema（仅本切片用到的表）
2. 邮箱 + 密码的注册、登录、登出、会话
3. 邀请码：一人一码、用一次即失效；提供一条生成命令
4. 首次引导写入真实的资料与目标
5. 「我的」页读取真实资料与目标
6. 体重记录的写入与读取：**新增一个录入页 `/weights/new`**（与 `/meals/new`、`/workouts/new` 同构），并在首页「今日空腹体重」卡与趋势页体重表读取
7. 数据访问层 `lib/db/`，所有查询强制带 `userId`
8. 错误监控接入
9. 集成测试（认证、数据隔离、事务）

### 3.2 明确不做

- 帖子/社区/好友等社交功能
- 邮箱验证与密码自助找回
- 手机号注册（留待迁回国内时）
- 第三方登录（微信等；需要资质）
- 管理后台（邀请码用命令生成）
- 饮食、运动、训练计划的落库（计划 4、6）

## 4. 数据模型

### 4.1 只建本切片真正会用到的表

**不预建以后才用的表。** 理由：没人写入的表 = 没被验证过的设计；Prisma 加表很便宜，而一个从未被真实数据检验过的表结构，真用起来往往要改，那时再改更贵。

| 表 | 作用 | 谁写 |
|---|---|---|
| 认证表（**由认证库管理**） | 账号、密码哈希、会话 | 认证库 |
| `Profile` | 业务资料：姓名、身高、年龄、性别、活动量、开始使用日期 | 首次引导 |
| `Goal` | 目标：方向、热量/蛋白/碳水/脂肪/运动消耗、目标体重 | 首次引导、「我的」页 |
| `WeightEntry` | 一条体重记录：用户、日期、体重。**同一用户同一天只允许一条**（`(userId, date)` 唯一约束；重复录入为更新） | 体重录入页 |
| `InviteCode` | 邀请码：码值、是否已用、使用者、创建时间 | 命令生成 |

**延后**：`Food`、`FoodEntry`（计划 4）；`ExerciseType`、`ExerciseEntry`、`StrengthSet`、`TrainingPlan`、`PlanDay`、`PlanItem`（计划 6）。

这些表的形状规格第 6 节已设计过，且 `lib/data/types.ts` 里的类型本就按可落库的形状书写，schema 可从现有类型推导。

### 4.2 认证表与业务资料分表

认证库自带 user 表（邮箱、密码哈希）。**业务字段不加入该表**，另建 `Profile` 与之一对一。

**理由**：认证库的表由其自行管理迁移。把业务字段塞进去，日后升级该库时，业务字段与库的迁移会相互纠缠——而开发者无法审代码，这类纠缠是最难排查的一类问题。

代价：读资料时多一次关联查询，开销可忽略。

### 4.3 三个继承自规格的决定

| 规格决定 | 在 schema 中的体现 |
|---|---|
| **营养值存快照** | `FoodEntry` 自带一份营养数值，不只存 `Food` 外键——历史记录不被后来的数据修正改动 |
| **日期用日期类型，不用时间戳** | `WeightEntry.date`、`FoodEntry.date` 均为纯日期；「今天」由客户端按本地时区算好后传入 |
| **份量内部统一用克** | `FoodEntry.grams`；界面上的「一碗」「两个」在写入前换算 |

### 4.4 首次引导一并收集性别与活动量

规格第 2.1 节要求首次引导收集**性别与活动量**（热量公式的输入），但当前引导页只收身高/体重/年龄。本计划既然要重写引导页写入真实数据，**一并收齐**。

代价：这两个字段会**先存着、暂时不用**（公式在计划 3 实现）。收益：避免计划 3 再改一次表单，并关掉规格中「资料页缺性别与活动量」的缺口。

## 5. 认证与邀请码

### 5.1 注册链路

```
邮箱 + 密码 + 邀请码
  → 校验邀请码：存在？未被使用？
  → 【同一个数据库事务内】占用邀请码 + 创建账号
  → 建立会话（cookie）
  → 跳转首次引导
```

**占用邀请码与创建账号必须在同一个事务内。** 否则两个人同一瞬间用同一个码注册可能双双成功——这是只在并发下出现、平时测不出来的缺陷。

密码由认证库哈希，**代码中不出现明文密码**。

### 5.2 会话

- 会话走 **httpOnly + secure + sameSite** 的 cookie，由认证库管理
- 未登录访问任何应用内页面 → 跳转 `/login`
- 登录成功后跳回原本要去的页面

### 5.3 邀请码

- **一人一码、用一次即失效**（规格第 6 节的 `InviteCode` 字段即为此设计）
- **生成方式**：一条命令，生成 N 个码并打印。不做管理界面。
- 记录使用者与使用时间

## 6. 数据访问层与页面接线

### 6.1 隔离靠「每个查询都带 userId」

新建 `lib/db/`。**页面不直接写 Prisma 查询**，只调 `lib/db/*` 中的函数；每个函数**第一个参数即 `userId`**，且不从任何全局读取：

```ts
export function listWeights(userId: string, from: string, to: string) { … }
```

**两个好处**：隔离逻辑集中在**一处**，而非散在 11 个页面里靠人记得加条件；隔离**可以被测试**——用两个用户交错读写，断言互不可见。

**这是本设计最需要警惕的一点**：新增查询若忘记带 `userId`，就是越权。它无法靠代码审阅兜住（开发者不读代码），只能靠集成测试。

### 6.2 哪些页面接真

| 页面 | 本计划之后 |
|---|---|
| `/login` | **真实**注册登录 |
| `/onboarding` | **真实**写入资料与目标 |
| `/me` | **真实**读资料与目标，并显示邮箱 |
| `/weights/new` | **新增**：体重录入页（demo 里没有录入入口，体重一直是生成的） |
| 首页「今日空腹体重」卡 | **真实**读；点击进入录入页 |
| 趋势页「体重」表 | **真实**读写 |
| 首页其余（饮食、运动、训练计划） | 仍假数据 |
| 趋势页「热量盈余」表 | 仍假数据 |
| 日历页、某日详情页 | 仍假数据 |

### 6.3 假数据与真实数据并存

`lib/data/`（假数据）与 `lib/db/`（真实数据）**并存一段时间**，直到计划 4、6 各自把对应模块接真。这是刻意安排，不是遗留垃圾。

**已确认接受的过渡状态**：新注册用户打开趋势页会看到——**体重表是空的，下面热量盈余表有 366 行假数据**，同屏一空一满。接受的理由是它证明了本切片的核心闭环：**记一条体重 → 在趋势里真的看到它**。该观感会在计划 4 之后自然消失。

## 7. 错误处理

| 情况 | 处理 |
|---|---|
| 邮箱已注册 | 提示「该邮箱已注册」并给出登录入口。代价：暴露某邮箱是否注册过；邀请制下风险低而体验更好 |
| 邀请码不存在 / 已被使用 | **分别提示**，后者说明「这个码已经被人用了」 |
| 密码不符合要求 | 明确说明差在哪，不笼统提示「格式错误」 |
| 未登录 | 跳转 `/login`，并记住原本要去的页面，登录后跳回 |
| 数据库连不上 | 显示「暂时无法加载」并上报错误监控，**绝不白屏** |
| 会话过期 | 同未登录 |

## 8. 测试策略

### 8.1 分两层，两条命令

| 层 | 依赖 | 命令 |
|---|---|---|
| 单元测试（现有 176 条） | 无 | `npm test`，保持秒级 |
| 集成测试（认证、数据隔离、事务） | 一个**专用的云数据库** | 单独一条命令 |

两条命令在**交付前都必须全绿**（`AGENTS.md` 的要求）；日常改前端时不必等数据库。

### 8.2 明确不使用 SQLite 跑测试

SQLite 零安装、很诱人，**但 SQLite 与 Postgres 不是同一个数据库**。而本计划要测的恰恰是两者差异最大的地方：**并发与事务**（见 5.1 的邀请码竞态）。用 SQLite 测出的「通过」对 Postgres 没有意义——这正是「测试对着假东西通过、上线才发现不一样」的典型。

代价：集成测试**需要联网**；免费额度的云数据库空闲会休眠，首次查询会慢几秒。

### 8.3 必须覆盖的测试

- **数据隔离**（最重要）：两个用户交错写入与读取，断言互不可见
- **邀请码竞态**：并发使用同一个码，只允许一个成功
- **注册链路的原子性**：事务中任一步失败，邀请码不被占用
- **未登录拦截**：未登录访问应用内页面跳转 `/login`，且登录后跳回原页面
- **体重读写往返**：写入一条体重，能在趋势页读到
- **同日重复录入**：同一天录入两次，只保留一条（更新而非新增）
- 会话过期后的行为

## 9. 运维可见性

**本计划接入错误监控**（Sentry 或同类，有免费额度）。

规格第 11 节将错误监控列为**独立运维的前提、不是可选项**。本计划是项目第一次真正对外提供服务——从此程序出错不再是「刷新一下」，而是「有人用不了」。而开发者无法自行复现与定位，错误监控是唯一能看到真相的地方。

## 10. 已知限制与取舍

| 限制 | 原因 | 何时处理 |
|---|---|---|
| 境外托管，国内访问可能慢或不稳 | 换取零资质、零备案、当天可跑 | 正式公开前迁移到国内云 + 域名备案 |
| 邮箱不验证 | 邀请码即门槛，省掉邮件服务与 SPF/DKIM 配置 | 公开注册前 |
| 忘记密码无法自助找回 | 不发信 | 公开注册前 |
| **数据隔离靠「每个查询带 userId」** | 设计如此 | 持续靠集成测试守护 |
| 饮食、运动、训练计划仍是假数据 | 分别为计划 4、6 | 计划 4、6 |
| 注册用邮箱而非手机号 | 避开短信服务的实名与按条计费 | 迁回国内时 |
| 过渡期趋势页「一空一满」 | 体重已接真、饮食未接真 | 计划 4 |

## 11. 待确认事项

以下事项**在本设计文档编写时未能完成核实**，实现前必须解决：

1. **认证库的最终选型。** 两轮网络搜索的**标题**一致指向 Better Auth 作为 Next.js 的邮箱+密码方案，备选为 Auth.js（NextAuth）。但本环境的网络策略拦截了 `WebFetch`，**我无法打开任何一篇正文**，因此无法核实现成度、邮箱+密码是否为一等公民、与 Next.js 16 的兼容性、以及它的表结构。
   **本文档不把具体库写进设计**——按 4.2 的要求，选型需先确认该库是否允许独立的业务资料表。
2. **托管 Postgres 的最终选型。** 搜索标题指向 Neon 与 Supabase 两条路线；**免费额度的具体限制（存储、计算时长、连接数）、是否提供独立测试库的机制（如分支）、以及与 Prisma 的配合方式，均未核实。**
3. **错误监控服务的选型与免费额度。** Sentry 或同类，未核实。
4. **云数据库的测试库如何与生产隔离。** 需要确认所选托管商是否支持独立数据库或分支，避免集成测试污染生产数据。

> 处理原则与规格第 8 节那条未核实的热量公式一致：**方向可以定，未核实的细节不写进设计**。写成既定事实的东西，将来改起来比一开始就标注「待核实」贵得多。
