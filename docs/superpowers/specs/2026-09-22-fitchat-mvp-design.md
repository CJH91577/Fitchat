# Fitchat MVP 设计文档

- **日期**：2026-09-22
- **状态**：待评审
- **范围**：MVP（邀请制）

---

## 1. 项目概述

Fitchat 是一款面向中文用户的饮食与健身管理 Web 应用。MVP 的核心目标是验证一件事：**用户是否愿意每天记录饮食和运动，并根据反馈调整行为。**

### 成功标准

MVP 以邀请制上线，成功标准是：

1. 邀请的十几位真实用户中，有相当比例能连续使用一周以上（而非注册后即流失）
2. 记录一条饮食的操作能在 3 步内完成，用户不觉得麻烦
3. 营养数据不出错到影响信任的程度

不追求用户规模。这个阶段的目的是**验证产品是否成立**，以及验证开发者和维护者是否应付得来。

### 目标用户

面向**健身人群**，涵盖三类目标：**增肌**、**减脂**、**体重管理（维持）**。

由此产生四条设计约束：

1. **目标设定必须支持三种方向**：减脂为热量赤字、增肌为热量盈余、维持则不做调整。**不可默认赤字。**
2. **蛋白质摄入是核心指标之一**，对增肌人群尤其如此，故列入圆环。
3. **力量训练必须支持记录重量与组数**。只有「时长」无法让增肌人群判断自己是否在进步，而进步追踪正是该人群的核心诉求。
4. **体重曲线的方向不带有好坏含义**。增肌期体重上涨是预期结果，界面若把上涨渲染为负向（红色、向下箭头等），会直接冒犯增肌用户。方向的好坏需依据用户设定的目标来判断。

## 2. 范围

### 2.1 MVP 做什么

| # | 功能 | 说明 |
|---|---|---|
| 1 | 注册 / 登录 | 需邀请码才能注册 |
| 2 | 个人资料与目标 | 身高、体重、年龄、性别、活动量、**目标方向（增肌 / 减脂 / 维持）** → 每日热量与营养素目标；设定目标体重 |
| 3 | 饮食记录 | 搜索食物 → 选份量 → 归入早/午/晚/加餐 |
| 4 | 食物数据 | 开放数据源导入 + 自建中文常见食物库 |
| 5 | 自然语言记饮食 | 「中午吃了两个鸡蛋一碗米饭」→ 模型拆成条目 → 用户逐条确认后入库 |
| 6 | 运动记录 | 有氧：类型 + 时长 + 强度；力量：动作 + 若干组「重量 × 次数」。两者均估算消耗 |
| 7 | **训练计划** | 用户自行编排周计划：每天练什么、哪些动作、目标组数与次数区间。首页显示「今天该练什么」，可据计划一键记录 |
| 8 | 体重记录 | 定期录入，看趋势曲线 |
| 9 | 今日看板 | 四个圆环 + 净热量 + 当天计划 + 当日记录摘要 |
| 10 | 历史与趋势 | 7 / 30 / 90 天统计 + 月历视图 |

**关于第 6 项的路径划分：** 运动模块分为两条路径——

- **有氧**：类型 + 时长 + 强度 → 估算消耗
- **力量**：动作 + 若干组「重量 × 次数」→ 估算消耗

**仍然不做**：动作库的后台管理、渐进超负荷分析与进步曲线、组间休息计时、系统推荐训练计划（计划由用户自行编排）。这些合起来构成一个完整的训练管理系统，属独立子项目。

**关于第 7 项（训练计划）：** 计划是**用户自行编排的输入**，系统不生成计划、不评价计划。MVP 阶段计划的用途只有两个——告诉用户今天该练什么，以及让记录训练时能少点几下。**「计划效果好不好」属第二期，见第 14 节。**

> **范围修订记录：** 本节最初将运动模块收窄为「类型 + 时长 + 强度」。该结论建立在「目标用户为减脂人群」这一假设之上，而该假设随后被推翻。目标用户确认为涵盖增肌的健身人群后，**力量训练的重量与组数成为不可省略的需求**，故修订为上述两条路径。

### 2.2 明确不做

社区动态、拍照识别食物、条码扫描、可穿戴设备同步、动作库后台管理、系统推荐训练计划、渐进超负荷分析、组间休息计时、**训练效果分析（第二期，见第 14 节）**、好友与排行榜、打卡分享、付费订阅、多语言、离线支持。

这份清单与「做什么」同等重要——每增加一项，拿到可用产品的时间就相应推后。

## 3. 核心设计理念

### 3.1 饮食与运动通过「净热量」绑成一个闭环

```
净热量 = 摄入热量 − 运动消耗热量
```

饮食记录往上加，运动记录往下减，体重曲线是结果。**两个模块不是并列关系，而是同一个闭环的两侧。** 这是「双核心」在 MVP 中的正确接法，避免做成两个互不相干的半成品。

### 3.2 四个圆环

参考 Apple Fitness 的信息结构：以同心圆环将多个目标压缩为一眼可读的状态，「把环合上」本身即构成激励机制。

| 环 | 指标 |
|---|---|
| 外环 | 热量摄入 / 每日目标 |
| 中环 | 运动消耗 / 目标 |
| 内环 | 蛋白质 / 目标 |
| 最内环 | 碳水 / 目标 |

**蛋白质为什么必须在环上：** 它同时服务三类目标用户——减脂期保住肌肉、增肌期支撑合成、维持期保证基本摄入。它是唯一一个在三类目标下都关键的营养素，因此优先级高于碳水。

**脂肪不进环**，仅在当天详情的营养素明细中展示。理由：四个环已是手机小屏的可读上限，环数继续增加会导致每个环细到无法辨认。

### 3.3 借鉴的信息结构 vs. 不借鉴的视觉外观

借鉴：圆环作为主视觉、可滚动分区卡片、历史页的月历 + 状态点、趋势升降箭头。

不借鉴：配色、动效、字体等具体视觉表达。圆环是苹果辨识度极高的设计，受商业外观保护。本项目取其交互模式，走自有视觉语言。

## 4. 技术方案

### 4.1 总体架构

```
手机浏览器 (H5)
      │
      ▼
Next.js 单体应用（页面 + 接口同项目）
      │
      ├──▶ 托管 Postgres (Prisma ORM)
      │
      └──▶ DeepSeek API  ← API Key 仅在服务端，不下发浏览器
```

### 4.2 技术选型及理由

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | Next.js（App Router）+ TypeScript | 前端页面与后端接口同一项目，无需分别部署、无需处理跨域 |
| ORM | Prisma | 类型安全，迁移管理成熟 |
| 数据库 | 托管 Postgres | 不自行安装与维护数据库 |
| 认证 | 成熟的现成方案 | 不自行实现登录逻辑 |
| 部署 | 托管平台，一条命令 | 无服务器需要管理 |
| 错误监控 | 第三方服务（如 Sentry） | 见第 11 节 |

**选型总原则：** 开发者本人不写代码、无法独立调试，因此一律选择主流、生态成熟、公开资料丰富的技术栈——冷门方案出问题时查不到答案，这会成为主要障碍。同理，一律使用托管服务，不自建基础设施。

### 4.3 目录结构（草案）

```
app/
  (auth)/login          登录、邀请码注册
  (app)/today           首页（四环 + 今日记录）
  (app)/trends          趋势页（7/30/90 天 + 月历）
  (app)/me              资料与目标
  api/
    foods/search        搜索食物库
    foods/parse         自然语言解析（调用 DeepSeek）
    entries/*           记录的增删改查
lib/
  db/                   Prisma schema 与数据访问
  nutrition/            热量与营养素计算、校验规则
  ai/                   DeepSeek 客户端、提示词、缓存
  goals/                目标计算
components/
  rings/                圆环组件
```

### 5.3 其余界面

| 界面 | 关键设计 |
|---|---|
| 登录/注册 | 邀请码是唯一门槛；填错时给出明确提示 |
| 首次引导 | 填资料 → **选择目标方向** → 展示算出的每日目标 → 允许手动微调 |
| 添加饮食 | 搜索框 + 「用一句话描述」双入口 |
| 添加运动 | 有氧：类型 → 时长 → 强度；力量：动作 → 逐组录入「重量 × 次数」 |
| 训练计划 | 周计划编排：为每天设定主题、添加动作、填目标组数与次数区间。可一键「开始记录」，计划内容预填为实际记录 |
| 我的 | 资料、目标、退出。低频，最简 |

### 5.4 三个决定成败的交互细节

**其一：添加饮食必须支持两种输入方式。**

搜索适合「我知道我要找什么」；而真实场景中用户往往是「刚吃完，懒得搜」。因此搜索框下方直接提供「用一句话描述你吃了什么」，走模型解析。

**解析结果必须是可编辑的列表，用户逐条确认后才入库。** 模型会认错食物、会估错份量，让用户确认既是兜住错误的关键机制，也让用户对数据保有掌控感。

**其二：AI 估算的条目必须视觉可辨。**

来自食物库的条目显示确切营养值与数据来源；来自模型估算的条目带明显标记（如「AI 估算」标签与不同底色），点开可看到说明。这不是装饰——用户需要知道哪些数字可信、哪些只是粗估，否则整个应用的数据可信度会被拉低到估值的水平。

**其三：体重变化的方向不做好坏着色。**

界面**不得**用红色表示上涨、绿色表示下降。原因是本产品同时服务增肌与减脂人群，**对增肌用户，体重上涨正是目标**；用「下跌 = 好」的视觉语言，会把一半用户的成功渲染成失败。

正确做法：方向的含义由用户设定的目标决定。增肌期的上涨、减脂期的下降，都应以中性或正向的方式呈现，并在需要时明确标注「符合当前目标」。

同理，第 5.1 节首页 mockup 中的「↓0.3」只是数值变化，**不带颜色语义**。

## 6. 数据模型

### 6.1 实体

| 实体 | 作用 | 关键字段 |
|---|---|---|
| **User** | 账号与身体资料 | 身高、体重、年龄、性别、活动量 |
| **Goal** | 目标设定 | **目标方向（增肌 / 减脂 / 维持）**、热量 / 蛋白 / 碳水 / 脂肪 / 运动消耗目标、目标体重 |
| **Food** | 食物库条目 | 名称、每 100g 营养值、**数据来源**、份量换算 |
| **FoodEntry** | 一条饮食记录 | 用户、日期、餐次、食物、份量、**营养值快照** |
| **ExerciseType** | 运动 / 动作字典 | 名称、类别（有氧 / 力量）、MET 值 |
| **ExerciseEntry** | 一次训练记录 | 用户、日期、运动类型、时长、**消耗快照** |
| **StrengthSet** | 力量训练中的一组 | 所属训练记录、序号、重量、次数 |
| **TrainingPlan** | 一份训练计划 | 用户、名称、是否启用 |
| **PlanDay** | 计划中的某一天 | 所属计划、星期（1–7）、训练主题（如「胸 + 三头」） |
| **PlanItem** | 某天的某个动作安排 | 所属 PlanDay、动作、目标组数、目标次数区间、排序 |
| **WeightEntry** | 一条体重记录 | 用户、日期、体重 |
| **InviteCode** | 邀请码 | 码值、是否已使用、使用者 |

`Food` 的数据来源字段区分四种：开放数据源 / 自建中文库 / 用户自定义 / AI 估算。

`ExerciseType` 同时承担两种角色：有氧运动类型（跑步、骑行、游泳……）与力量动作（深蹲、卧推、硬拉……）。**MVP 不做动作库的后台管理**，而是预置一份常见动作列表，并允许用户自行添加动作名（自定义名称随用户隔离，不进入公共字典）。

**力量记录的层次结构：**

```
ExerciseEntry（一次训练：9月22日 · 胸部训练）
  ├── ExerciseType：卧推
  │     ├── StrengthSet  组1  60kg × 12
  │     ├── StrengthSet  组2  70kg × 10
  │     └── StrengthSet  组3  70kg × 8
  └── ExerciseType：上斜哑铃卧推
        └── StrengthSet  组1  22kg × 12
```

即：**一次训练包含若干动作，每个动作包含若干组。** 之所以把「组」独立成实体而非塞进数组字段，是因为每一组的重量与次数都需要被单独查询与统计——将来做进步曲线时，查询的是「卧推这个动作、重量随时间的序列」，独立实体才能高效支持。

**训练计划的层次结构：**

```
TrainingPlan（我的增肌计划 · 启用中）
  ├── PlanDay  周一 · 胸 + 三头
  │     ├── PlanItem  卧推          4 组 × 8–10 次
  │     ├── PlanItem  上斜哑铃卧推   3 组 × 12 次
  │     └── PlanItem  绳索下压       3 组 × 15 次
  ├── PlanDay  周二 · 休息
  └── PlanDay  周三 · 背 + 二头
        └── ...
```

**计划与记录是两套东西，不可混同：** `PlanItem` 是「计划要做多少」，`StrengthSet` 是「实际做了多少」。二者对应但独立存在——用户可能没按计划练（换动作、加组、减重），**记录必须反映实际发生的，而不是计划的**。首页显示「今天该练什么」时读取计划；用户点「开始记录」时，计划内容作为预填充值带入，用户可任意修改。

MVP 阶段一个用户只有一份启用中的计划，但数据结构支持多份（便于将来做周期切换）。

### 6.2 三个必须固化的设计决定

**其一：营养值存快照，不做实时联表。**

记录一条饮食时，将当时的营养数值复制一份存进记录本身，而非在展示时联表查询食物库。

原因：食物库数据后期必然会被修正（发现某条目录错误、开放数据源更新）。若历史记录实时联表，**用户三个月前那天的热量会莫名改变。历史必须冻结。** 运动消耗同理。

**副作用（刻意取舍）：** 用户无法追溯修正历史记录的营养值。这是为换取历史稳定性而付出的代价。

**其二：「日期」使用日期类型，不使用时间戳。**

用户所说「今天」按其所在时区计算。存时间戳会在跨时区、跨夏令时场景下算错日子。因此记录上直接存日期（年月日），「今天」由客户端按本地时区算好后传入。

**其三：份量统一以克为内部单位。**

用户看到的是「一碗」「两个」「一份」，内部统一换算为克存储。否则跨食物份量比较、营养计算、统计聚合都会退化为一堆特例。

### 6.3 目标历史版本

**MVP 不保留目标的历史版本。** 用户修改目标后，历史日期的达标标记会按新目标重算。

这是 YAGNI 取舍：邀请制阶段用户数量极少，几乎不会触及。此限制已记录于第 12 节，后续需要时再引入按日快照。

## 7. AI 层设计（DeepSeek）

### 7.1 定位

**大模型是理解层，数据库是事实层。**

大模型产出的是「看起来合理的数字」，而非经过查证的事实。营养数值属精确事实，模型未在这些数字上做过核对。因此：

- **可查到的一律用数据库值**，且可溯源
- **查不到时才走模型估算**，且必须明确标注

### 7.2 两个调用点

| 调用点 | 用途 | 失败时的行为 |
|---|---|---|
| 自然语言解析 | 「中午吃了两个鸡蛋一碗米饭」→ 结构化条目列表 | 提示后降级为纯搜索模式 |
| 兜底估算 | 食物库查不到时估算营养值 | 提示该条目为估算值 |

此外，模型亦可用于将用户口语化表述（如「番茄炒蛋」）模糊匹配到库中标准条目。

### 7.3 四个让 AI 层可信的设计

**其一：模型输出必须过校验，不得直接入库。**

模型可能返回格式错误、份量离谱（如「3 公斤米饭」）、或数值超出物理可能。所有模型返回都需经过一层结构化校验，方可进入下一步。

**其二：用营养素勾稽关系验算热量。**

蛋白质 4 kcal/g、碳水 4 kcal/g、脂肪 9 kcal/g（Atwater 系数）。三者的加权之和应当接近模型给出的总热量。

若模型称「100 克某食物 80 千卡」却同时报「蛋白质 30 克」（仅此一项即对应约 120 千卡），该数据在数学上自相矛盾，判定为可疑并拒绝。

**此校验为纯计算，不花钱、不依赖模型、不引入延迟**，可挡掉相当一部分幻觉数值。这是第 7.1 节顾虑的技术解法。

**其三：结果缓存，重复查询返回同一值。**

同名食物第二次查询直接命中缓存。既节省成本与时间，也**顺带压制了「同一食物两次查询数值不同」的问题**——至少在用户视角下结果是稳定的。

**其四：模型不可用时必须能降级。**

DeepSeek 超时或报错时，自然语言入口给出提示并退回纯搜索模式。**不可让整个记录功能随之失效**——记录饮食是核心流程，不能押在第三方服务的可用性上。

## 8. 目标计算

采用**《中国居民膳食指南（2022）》/《中国居民膳食营养素参考摄入量》**中的能量需要量数据，而非直接套用西方公式。

理由：本产品面向中文用户、以中式饮食为主，中国营养学会的标准更贴合目标人群。

### 8.1 必须先确定目标方向

用户在首次引导中选择目标方向，**这一步决定后续所有热量调整的正负号**：

| 目标方向 | 热量调整 | 说明 |
|---|---|---|
| 减脂 | 在需要量基础上**下调** | 制造热量赤字 |
| 增肌 | 在需要量基础上**上调** | 制造热量盈余 |
| 维持 | **不做调整** | 保持当前体重 |

**默认值不得设为减脂。** 用户未选择时必须明确询问，而非替其假定。

蛋白质目标同样随方向变化——增肌期与减脂期的蛋白质需求均高于维持期。

> **待核实项（重要）**：本文档编写时，权威来源站点（cnsoc.org、地方卫健委站点）因网络策略限制无法访问，**具体常数未能完成核对**。因此本文档不写入未经查证的数字。
>
> 实现前必须确认：能量需要量的取值方式（按年龄/性别/身体活动水平的参考值表，或基础代谢公式 × 活动系数）、活动水平分级与系数、减脂与增肌各自的调整幅度、以及三类目标下的蛋白质摄入建议。**该项应在实施计划的早期完成，因为它影响首次引导的产出结果。**

无论采用哪种方式，**计算结果必须允许用户手动微调**——公式给出的是估计值，用户的真实需求只有用户自己知道。

## 9. 测试策略

### 9.1 为什么对本项目格外关键

开发者不读代码，**测试是唯一可获得的质量信号**。实现质量无法靠阅读代码判断，只能由测试结果与可实际运行的产物来证明。这与 `AGENTS.md` 中「必须编写或更新相关测试并确保全部通过」的要求一致。

### 9.2 三层

| 层 | 测什么 | 说明 |
|---|---|---|
| 单元测试 | 计算公式 | 目标热量计算、营养素勾稽校验、份量换算。纯函数，回报最高 |
| 集成测试 | 接口 + 数据库 | 使用独立测试数据库，验证操作确实落库 |
| 端到端 | 关键流程 | 注册 → 记一餐 → 环更新（自动化浏览器） |

### 9.3 重点覆盖

- **每个计算公式都有已知输入输出的用例。** 热量数字错误会使整个产品失去意义，这是最不能靠感觉的部分。
- **营养素勾稽校验需专门喂入畸形数据**，确认其确实会拒绝。
- **日期与时区边界**：「今天」「昨天」「跨零点记录」最易出现隐蔽缺陷。

### 9.4 明确不测

- UI 像素级外观
- DeepSeek 的真实调用（慢、有成本、结果不确定）

### 9.5 AI 部分如何测试

将模型返回**录制为固定的假数据回放**，测试对象是**拿到返回之后的处理逻辑**（校验、入库、标注）。如此测试快速、稳定、零成本，且能覆盖「模型返回垃圾数据」这类真实故障场景。

## 10. 错误处理

| 情况 | 处理 |
|---|---|
| 用户输入有误 | 明确指出哪一项不对、应如何修改。如邀请码错误 |
| 外部服务故障 | DeepSeek 不可用则降级为纯搜索，界面告知「智能解析暂不可用」 |
| 程序内部错误 | 记录完整日志，向用户展示一句人话提示，**绝不白屏** |

原则：出错时必须让用户知道**哪一步失败了、可以怎么办**，而不是一个无响应的界面。

## 11. 运维可见性

本项目的真实风险不在开发阶段，而在上线之后：服务由一位不写代码、无法独立调试的人维护。用户数据异常、服务中断、数据算错，都需要有人能定位。

**因此必须接入错误监控服务**（如 Sentry 类工具），使程序异常自动上报、汇总并告警。

区别是实打实的：

- **没有它**：用户说「打不开了」，只能回复「我看看」
- **有它**：打开面板即可看到「9 月 22 日 14:03，数据库连接超时，影响 3 个用户」

这是独立运维该服务的前提，**不是可选项**。免费额度对 MVP 量级通常够用。

## 12. 已知限制与取舍

| 限制 | 原因 | 何时需要处理 |
|---|---|---|
| 改目标后历史达标标记按新目标重算 | 不做目标历史版本，简化实现 | 用户反馈受到困扰时 |
| 历史记录的营养值无法追溯修正 | 存快照以保证历史冻结 | 出现食物库数据错误时 |
| 运动模块不含动作库后台管理、系统推荐计划、渐进超负荷分析 | 控制 MVP 范围 | 核心闭环验证成立后单独立项 |
| 训练计划需用户自行编排，系统不生成也不评价 | 计划生成与效果评价属第二期 | 见第 14 节 |
| 力量训练有记录、无分析 | MVP 只存「重量 × 次数」，不做进步曲线与趋势判断 | 增肌用户提出需要时，优先级高 |
| 力量训练的消耗估算误差较大 | 力量训练的能耗受组间休息、动作节奏影响，任何应用都难以精确估算 | 长期存在，需在界面上说明 |
| 一个用户只有一份启用中的计划 | MVP 简化；数据结构已支持多份 | 用户提出周期切换需求时 |
| 自定义动作名不进入公共字典 | 每个用户独立，避免未审核内容进入公共数据 | 出现用户间共享需求时 |
| 脂肪不在圆环中展示 | 四环为小屏可读上限 | 视用户反馈 |
| 无离线支持 | 纯在线 H5，降低复杂度 | 用户抱怨弱网不可用时 |

## 13. 待确认事项

5. **短信/邮箱等注册验证方式**是否必要，或邀请码即可满足。

## 14. 第二期：训练效果分析

本节记录本次讨论的结论，目的是**使第二期立项时无需重新推导**。

### 14.1 为什么不在 MVP

**其一，逻辑上依赖数据积累。** 效果分析需要数周乃至数月的记录才有意义。在记录闭环尚未验证成立之前就开始做分析，是在沙子上盖楼——数据都还没稳定产生，分析的对象是什么？**这是主要理由，不是工作量问题。**

**其二，归因困难。** 体重与体成分的变化同时受饮食、训练、睡眠、水分、女性生理周期影响。仅凭饮食与训练记录，**很难把结果归因到某个训练计划**。若系统给出「你的计划有效 / 无效」的结论，它很可能是错的，而用户会当真并据此调整训练。这是会伤到人的错误。

**其三，合规风险升级。** 给出训练建议比记录数据责任更重，第 13 节的合规待确认项因此权重上升。

### 14.2 目标分类：入口话术与计算分类必须分离

产品表达上可以使用「男生增肌 / 女生塑形」这类用户听得懂的入口话术。

**但分析引擎不得以「塑形」作为计算分类。** 生理上不存在「塑形」这一目标——一位希望塑形的女性，实际进行的是减脂、增肌，或身体成分重组（同时增肌减脂）。若分析引擎中存在「女性塑形模式」，其内部公式只能凭空编造。

**正确做法：**

| 层级 | 分类 |
|---|---|
| 入口话术（用户可见） | 男生增肌 / 女生塑形 / 减脂 等产品化表达 |
| **计算分类（引擎内部）** | **增肌 / 减脂 / 身体成分重组** —— 仅此三类 |

入口话术向计算分类做映射，映射关系可以随产品迭代调整；**计算逻辑只针对三个生理目标编写。**

### 14.3 立项前必须解决

1. **明确「有效」的定义**——效果分析是一个开放问题，不是一个功能。必须先把「计划有效」转化为可计算的指标（如：在饮食达标的前提下，训练量是否按预期递增）。
2. **积累足够的真实数据**——需要先有数月的真实用户记录。
3. **评估是否需要引入专业人士**——涉及健康建议时，营养师或教练的参与可能不只是产品加分项，而是必要项。
4. **重新评估合规要求**——见第 13 节。
