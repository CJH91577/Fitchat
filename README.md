# Fitchat

![CI](https://github.com/CJH91577/Fitchat/actions/workflows/ci.yml/badge.svg)

移动优先的 H5 饮食与健身记录应用：记下每天吃了什么、练了什么，再看体重与热量盈余的变化。基于 Next.js + React + TypeScript + SQLite，**服务端渲染**，可以部署在一台普通服务器上。

**在线演示**：<https://fitchat.pages.dev>（旧的静态快照，已冻结；完整版部署见下方）

## 定位与范围取舍

这是一个**可用的项目**，范围是刻意收窄的：能注册登录、能记录、记录真的存在数据库里、页面之间的数据自洽。

已经做完的：

- **邀请码注册 + 邮箱口令登录**，会话在服务端（HttpOnly Cookie + `sessions` 表），每个页面都按登录用户取数；
- **写入有真实副作用**：记录饮食、记录运动、记录今日体重、首次引导生成的目标，全部落库并立刻反映到首页、日历与趋势；
- **一句话记饮食**是本地词表 + 量词换算（`lib/data/meal-parser.ts`），不是模型——所以它不给自己盖「AI 估算」的章，认不出的词原样退回给用户。

仍然刻意不做：接入大模型（没有 API 成本预算，也不该假装有）；训练计划的可视化编排（计划能读不能改）；社交与多用户协作。

## 技术栈

Next.js 16（App Router，服务端渲染）· React 19 · TypeScript 5 · **SQLite + Drizzle ORM** · CSS Modules（无 Tailwind）· Vitest + React Testing Library

## 运行

```bash
npm install
npm run db:seed   # 首次：建库 + 迁移 + 播种演示数据（约 1800 条记录）
npm run dev       # 开发服务器 http://localhost:3000
npm test          # 440 个单元/组件/页面测试
npm run lint      # ESLint 检查
npm run build     # 生产构建（standalone 产物）
npm start         # 以生产模式启动
npx playwright test   # 浏览器 E2E（先 npm run build；需要 playwright install chromium）
```

**演示账号**：`demo@fitchat.local` / `fitchat-demo`（口令是公开的，见下方「为什么演示账号没有门槛」）。三个随部署附送的一次性邀请码写在 `lib/db/demo.ts`，各能注册一个账号。

推送到 GitHub 后，CI 会自动执行 `test` / `lint` / `build` / 浏览器 E2E（见 `.github/workflows/ci.yml`）。

## 部署

**服务端渲染 + SQLite + Docker，部署在一台国内服务器（腾讯云）上。**完整步骤见 **[DEPLOY.md](DEPLOY.md)**。

- 数据是宿主机上的一个 SQLite 文件（挂载进容器），重建容器不丢数据；
- 应用首次启动时**自己建库**（迁移 + 播种），镜像里不需要额外的初始化步骤；
- 「今天」按请求计算，站点不会「过期」，**不需要每晚重建**。

## 认证：为什么是这样做的

- **口令用 Node 内置的 scrypt**，不引第三方库：镜像里用 `npm ci --ignore-scripts` 装依赖，bcrypt / argon2 这类需要编译的包在那里装不上。存储格式把成本参数一起写进去（`scrypt$N$r$p$salt$hash`），日后调高参数时老记录仍能验证。
- **库里存的是会话令牌的 SHA-256，不是令牌本身**：拿到库文件的人无法直接冒充登录。令牌是 32 字节随机数，退出登录就是删掉那一行（签名令牌做不到即时撤销）。
- **`password_hash` 为空时一律登录失败**，而不是「无需口令」——把「没有口令」当成「不需要口令」，等于给这类账号留一道后门。
- **登录失败只有一句话**（「邮箱或口令不正确。」），且账号不存在时也会跑一次 scrypt：否则登录页就是一台邮箱枚举器，响应快慢本身就是答案。
- **为什么演示账号没有门槛**：它的口令写在 README、登录页与 DEPLOY.md 里，而且点一下按钮就能进去。里面的数据全部是按日期确定性生成的假数据。把公开的口令包装成安全边界只是自欺欺人——要做的是把「真实账号」与「演示账号」分开，而那正是邀请码在做的事（每个码只能用一次）。

## 写入：为什么客户端说了不算

记录饮食的表单只提交**食物 id 与克数**，热量由服务端拿食物库重算；运动只提交时长与强度（或组数），消耗由服务端按同一套口径估。于是改浏览器里的那份 JSON 改不了自己记录里的数字。

删除的归属检查写在 SQL 条件里（`WHERE id = ? AND user_id = ?`），而不是把行查出来再比对：先查后删会在两次查询之间留一个窗口，而且一旦有人日后把查出来的结果换成别的东西，检查就静默失效了。删不掉时如实说「这条记录已经不在了」，不假装成功。

## 数据层

```
页面（服务端组件）
      │  只依赖 lib/db/queries.ts 这一个接口，全部是 async
      ▼
drizzle-orm/d1  ← 一个驱动，两种实现
      ├── 线上 / 本地 / 测试：lib/db/d1-shim.ts（在 better-sqlite3 上实现 D1 的接口）
      └── 将来若迁到 Cloudflare：真正的 D1 绑定（改动只在 lib/db/runtime.ts 一处）
```

数据库结构、迁移与种子数据都在 `lib/db/`；演示数据以日期为种子确定性生成，所以每次播种得到的都是同一个库。

## 测试：三条值得单独说的

- **`tests/css-modules-contract.test.ts`** —— 源码引用样式表里不存在的类名时，CSS Modules 返回 `undefined`，React 会直接省略该 `class` 属性：构建、lint、渲染测试**全部通过**，但布局静默失效。日历页曾因 `styles.calendarArea` 缺失导致网格完全没撑满，而所有自动化检查都是绿的。这条测试把「源码用到的类」与「样式表里定义的类」之间的契约钉住。
- **`lib/db/schema.test.ts`** —— 迁移 SQL 与 `schema.ts` 是两份独立的描述，漂移了不会有任何症状（构建通过、lint 通过、页面照常跑，直到某天查询报「no such column」）。这条测试把迁移应用到一个全新的库上，再逐表逐列与 Drizzle 的定义比对。
- **`lib/db/migrate.test.ts`** —— 迁移是在什么条件下执行的。起因是一次真实事故：把 `users` 的资料列改成可空需要重建表，而重建期间 `DROP TABLE users` 按 `ON DELETE CASCADE` 把演示用户的 1431 条饮食记录连同运动、体重一起删了，用户那一行还在。原因是 `PRAGMA foreign_keys` 在事务里是空操作，而迁移器把每个迁移包在事务里执行。现在外键在跑迁移的连接上是关的，迁移之后再用 `foreign_key_check` 拦下孤儿行；这条测试复现了老库的形状，去掉修复就会转红。
- **`e2e/demo-flow.spec.ts`**（Playwright）——唯一没有机器验证过的一步是「点登录按钮」：React 的 Server Action 协议没法手写请求（试过，回协议错误），组件级与 action 级测试都覆盖不到。这条 E2E 用真浏览器跑通「打开 → 一键进演示账号 → 记一条运动 → 首页看到它」，在 CI 里执行（`.github/workflows/ci.yml`）。

## 设计上的几个取舍

- **首页只有两个圆环**（热量、运动），圆心是净热量。蛋白质与碳水仍然记录，但不占首页的视觉重心——行为指标（吃多少、练多少）优先于结果指标。
- **体重涨跌不做好坏着色**：增肌期体重上涨是预期结果，用红色或向下箭头表示会直接冒犯增肌用户。
- **假数据以日期为种子确定性生成**，不用 `Math.random()`：同一个日期永远得到同一组数值，页面之间才不会互相矛盾。哈希在 FNV-1a 之后补了一步 32 位雪崩混合——只用 FNV-1a 时，28 个连续日期的取值会挤在 0.06~0.65 这样的窄带里。
- **未来日期的两种处理**：日历里今天之后的格子**不可点**（构建期没有那些页面时点进去是 404），某日详情页对未来的日期显示「这一天还没有到」——那与「那天没记录」是两件事。
- **圆环的半径常量是算出来的，不是调出来的**：圆心空腔必须容得下四位数的净热量，`RingGroup.test.tsx` 用几何断言钉住这层约束。
- **空环的底轨用 0.4 不透明度，而不是 0.18 的淡洗**：后者会把橙色环的色度压到填充色的 17%（实测 `#F9E1D7`，视觉上已是浅粉），而蓝色在同样比例下仍被认作蓝。测试用色度保留率守住这条。

## 已知限制

- **口令没有自助找回**（没有邮件服务）：忘记口令时由管理员在服务器上跑 `npm run reset-password -- --email …` 生成一次性重置码（24 小时有效），用户在登录页「忘记口令」里用它设置新口令。
- **邀请码只有三个随部署附送的名额**，用完为止；要发更多、查看谁用了、作废，用 `npm run invite`（见 DEPLOY.md 第四节）。
- **一句话记饮食只认词表里的食物**，且份量写在食物**前面**（「两个鸡蛋」认，「鸡蛋两个」不认）——认不出的部分会列出来，不会静默记成 100 克。
- **训练计划可以编辑**（每星期的主题与动作，改完首页与记录页的预填跟着变）；体重可以补记过去的日子（未来日期会被拒绝）。
- **没接大模型**：`pantry.ts` / `meal-parser.ts` 是词表与量词换算，估算出的热量只是粗估。
- **演示数据只覆盖到「最后续播日 + 90 天」**（多播是为了让站点打开就有内容，日历对未来日期的格子本来就是不可点的）。启动时会检查演示账号的最新记录日期，剩余不足 7 天就自动续播到「今天 + 90 天」——只补最新日期之后的区间，已有的行（包括用户改过、删过的）都不动。唯一的例外：站点连续运行超过 90 天且从未重启，续播没有机会执行，首页仍会显示「未记录」，重启容器即恢复。详细清单见[走查清单](docs/superpowers/plans/demo-走查清单.md)第四节。
